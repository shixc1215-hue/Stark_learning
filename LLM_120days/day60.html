🤖 为什么规则引擎还不够？LLM 质检的定位 ~10 分钟

昨天我们搭建了完整的规则引擎 — 空值检查、范围校验、唯一性约束……这些"硬规则"能精准捕获明确的逻辑错误。但数据质量问题远不止于此：

规则引擎擅长

空值率超过阈值
主键重复
数值超出 [min, max]
格式不符合正则
引用完整性违反

LLM 擅长

业务语义异常（字段值看似合法但不合理）
跨字段逻辑矛盾
数据漂移的深层原因
修复建议生成
非结构化异常识别

数仓思维映射：规则引擎 = ETL 中的 "约束检查阶段"（NOT NULL / CHECK / UNIQUE）；LLM 质检 = "数据探查 + 异常归因"（数据分析师人工做的事）。两者互补，不是替代。

📊实际案例对比

异常类型示例规则引擎LLM 质检

语义不合理贷款金额 100 元但资产评估 500 万 ❌ 看不出问题 ✅ 语义理解捕获

核心思路：先用规则引擎做"快速扫描"（毫秒级，覆盖 80% 常见问题），再用 LLM 对规则捕获的异常做"深度归因"，并对规则遗漏的问题做"语义补充检测"。
🐍 Python 知识：结构化输出 + 重试容错 + 随机采样 ~12 分钟

1️⃣ Pydantic 结构化输出（让 LLM 返回可解析对象）

LLM 质检的关键挑战：如何让 LLM 返回结构化的检测结果？Pydantic 模型 + JSON Mode 是标准解法。

from pydantic import BaseModel, Field
from enum import Enum
from typing import Optional

class Severity(str, Enum):
    LOW = "low"       # 轻微，建议关注
    MEDIUM = "medium" # 中等，需要确认
    HIGH = "high"     # 严重，必须修复
    CRITICAL = "critical"  # 致命，立即处理

# 单条 LLM 检测结果
class LLMAnomaly(BaseModel):
    """一条异常记录"""
    field_name: str = Field(..., description="异常字段名")
    row_values: dict = Field(default_factory=dict, description="相关行数据")
    anomaly_type: str = Field(..., description="异常类型，如 语义不合理/跨字段矛盾/值域漂移")
    description: str = Field(..., description="问题描述（人类可读）")
    severity: Severity = Field(..., description="严重程度")
    suggested_fix: Optional[str] = Field(None, description="修复建议")

# LLM 批量检测结果
class LLM检测结果(BaseModel):
    """LLM 对一批数据的质检结果"""
    anomalies: list[LLMAnomaly] = Field(default_factory=list)
    summary: str = Field("", description="整体数据质量评价")
    confidence: float = Field(0.0, ge=0.0, le=1.0, description="检测置信度")

# 实例化测试
result = LLM检测结果(
    anomalies=[
        LLMAnomaly(
            field_name="loan_amount",
            row_values={"loan_amount": 100, "asset_value": 5000000},
            anomaly_type="语义不合理",
            description="贷款金额100元但资产评估500万，比例异常",
            severity=Severity.HIGH,
            suggested_fix="核实贷款金额是否为笔误，可能是100万"
        )
    ],
    summary="发现1条语义异常，建议核实贷款金额",
    confidence=0.85
)
print(result.model_dump_json(indent=2))
# 输出格式化 JSON，可直接存入数据库或返回给前端

2️⃣ 随机采样策略（避免给 LLM 全量数据）

实际业务中一张表可能百万行，不可能全部发给 LLM。需要智能采样 — 既要覆盖异常，又不能太多。

import random
from typing import Any

def smart_sample(
    data: list[dict],
    suspicious_indices: list[int],  # 规则引擎标记的可疑行
    sample_size: int = 20,
    suspicious_ratio: float = 0.6   # 采样中可疑行占比
) -> list[dict]:
    """
    智能采样：混合正常行 + 可疑行
    数仓类比：就像 ETL 中先跑统计探查，再抽样人工检查
    """
    # 计算可疑行和正常行的采样数量
    n_suspicious = int(sample_size * suspicious_ratio)
    n_normal = sample_size - n_suspicious

    # 从可疑行中随机抽取（无放回）
    suspicious_pool = [data[i] for i in suspicious_indices if i < len(data)]
    sampled_suspicious = random.sample(
        suspicious_pool,
        min(n_suspicious, len(suspicious_pool))
    )

    # 正常行 = 全部数据 - 可疑行
    normal_indices = [i for i in range(len(data)) if i not in suspicious_indices]
    normal_pool = [data[i] for i in normal_indices]
    sampled_normal = random.sample(
        normal_pool,
        min(n_normal, len(normal_pool))
    )

    return sampled_suspicious + sampled_normal

# 使用示例
data = [
    {"id": 1, "loan_amount": 100, "asset_value": 5000000},   # 可疑
    {"id": 2, "loan_amount": 500000, "asset_value": 600000}, # 正常
    {"id": 3, "loan_amount": -100, "asset_value": 300000},   # 可疑（负值）
    {"id": 4, "loan_amount": 80000, "asset_value": 90000},   # 正常
]
suspicious = [0, 2]  # 规则引擎标记
sampled = smart_sample(data, suspicious, sample_size=4)
print(f"采样 {len(sampled)} 条，可疑行优先")
for row in sampled:
    print(f"  id={row['id']}, loan={row['loan_amount']}")
# id=1, id=2, id=3, id=4 — 可疑行优先被选中

3️⃣ 重试 + 降级容错（LLM 输出不可靠的处理策略）

import json
import re
from dataclasses import dataclass, field

@dataclass
class RetryResult:
    """重试结果：记录尝试过程"""
    success: bool
    data: Any = None
    attempts: int = 0
    errors: list[str] = field(default_factory=list)

def parse_llm_json_safely(
    raw_text: str,
    model_class: type,
    max_retries: int = 3
) -> RetryResult:
    """
    三层 fallback 解析 LLM 输出的 JSON：
    1. 直接 json.loads
    2. 正则提取 {...} 块
    3. 逐行修复常见格式错误（尾逗号/单引号）
    """
    for attempt in range(1, max_retries + 1):
        try:
            # 策略1：直接解析
            return RetryResult(
                success=True,
                data=model_class(**json.loads(raw_text)),
                attempts=attempt
            )
        except (json.JSONDecodeError, Exception) as e:
            pass

        try:
            # 策略2：正则提取最外层 JSON 对象
            match = re.search(r'\{.*\}', raw_text, re.DOTALL)
            if match:
                return RetryResult(
                    success=True,
                    data=model_class(**json.loads(match.group())),
                    attempts=attempt,
                    errors=[f"尝试{attempt}: 需正则提取JSON块"]
                )
        except Exception as e:
            pass

        try:
            # 策略3：修复常见格式错误
            cleaned = raw_text.strip()
            cleaned = re.sub(r',\s*}', '}', cleaned)      # 去掉尾逗号
            cleaned = re.sub(r',\s*]', ']', cleaned)      # 去掉数组尾逗号
            cleaned = cleaned.replace("'", '"')            # 单引号→双引号
            return RetryResult(
                success=True,
                data=model_class(**json.loads(cleaned)),
                attempts=attempt,
                errors=[f"尝试{attempt}: 格式修复后解析"]
            )
        except Exception as e:
            pass

    # 全部失败
    return RetryResult(
        success=False,
        attempts=max_retries,
        errors=[f"所有解析策略均失败"]
    )

# 测试：模拟 LLM 返回了带 markdown 标记的 JSON
raw = '```json\n{"anomalies": [], "summary": "数据质量良好", "confidence": 0.95}\n```'
result = parse_llm_json_safely(raw, LLM检测结果)
print(f"解析成功: {result.success}, 尝试次数: {result.attempts}")
print(result.data)  # LLM检测结果(anomalies=[], summary='数据质量良好', confidence=0.95)
注意：三层 fallback 的顺序很重要 — 先尝试最精确的解析，逐步放宽约束。每次只修复一种类型的问题，避免引入新错误。

🧠LLMDetector — LLM 语义质检器

import json
import requests
from dataclasses import dataclass, field
from typing import Optional

# --- 数据模型 ---

@dataclass
class LLMDetectionConfig:
    """LLM 质检配置"""
    api_url: str = "https://open.bigmodel.cn/api/paas/v4/chat/completions"
    model: str = "glm-4-flash"        # 轻量模型，质检任务够用
    api_key: str = ""                  # 从环境变量读取
    temperature: float = 0.1           # 低温度，减少随机性
    sample_size: int = 20              # 每次送 LLM 的样本数
    suspicious_ratio: float = 0.6      # 采样中可疑行占比
    max_retries: int = 2               # 解析重试次数

@dataclass
class FieldContext:
    """字段业务上下文（让 LLM 理解字段的业务含义）"""
    name: str
    description: str          # 业务含义
    normal_range: str         # 正常范围描述
    business_rules: list[str] = field(default_factory=list)

# --- LLM 质检器核心 ---

class LLMDetector:
    """
    LLM 驱动的语义质检器

    数仓思维：这就像让一个资深数据分析师
    看你抽样出来的数据，凭经验挑出"不对劲"的行
    """

    def __init__(self, config: LLMDetectionConfig):
        self.config = config

    def _build_detection_prompt(
        self,
        sample_data: list[dict],
        fields_context: list[FieldContext]
    ) -> str:
        """
        构建质检 Prompt — 关键是让 LLM 理解业务语义
        """
        # 字段上下文描述
        context_str = "\n".join([
            f"- {f.name}: {f.description}，正常范围 {f.normal_range}"
            + (f"。业务规则：{', '.join(f.business_rules)}" if f.business_rules else "")
            for f in fields_context
        ])

        # 样本数据（格式化为易读文本）
        data_str = json.dumps(sample_data, ensure_ascii=False, indent=2)

        return f"""你是一位资深的数据质量分析师，擅长发现数据中的语义异常和业务矛盾。

## 字段业务含义
{context_str}

## 待检查数据（共 {len(sample_data)} 条采样记录）
{data_str}

## 检查要求
请仔细审查每条记录，发现以下类型的问题：
1. **语义不合理**：字段值看似合法但不符合业务常理（如贷款100元但资产500万）
2. **跨字段矛盾**：字段之间存在逻辑矛盾（如结清日期早于入账日期）
3. **值域漂移**：某字段值与同批次其他记录相比显著偏离
4. **一致性异常**：关联字段值不匹配（如风险等级为"低"但逾期天数超过365天）

请以 JSON 格式返回结果，严格遵循以下结构：
```json
{{
  "anomalies": [
    {{
      "row_index": 0,
      "field_name": "字段名",
      "anomaly_type": "异常类型",
      "description": "详细问题描述",
      "severity": "low/medium/high/critical",
      "suggested_fix": "修复建议"
    }}
  ],
  "summary": "整体数据质量评价",
  "confidence": 0.85
}}
```
如果没有发现异常，anomalies 返回空列表。只返回 JSON，不要其他文字。"""

    def detect(
        self,
        data: list[dict],
        fields_context: list[FieldContext],
        suspicious_indices: list[int] | None = None
    ) -> RetryResult:
        """
        执行 LLM 语义质检

        Args:
            data: 全量数据
            fields_context: 字段业务上下文
            suspicious_indices: 规则引擎标记的可疑行索引（可选）
        """
        # 第一步：智能采样
        if suspicious_indices is None:
            suspicious_indices = []

        sample = smart_sample(
            data, suspicious_indices,
            sample_size=self.config.sample_size,
            suspicious_ratio=self.config.suspicious_ratio
        )

        # 第二步：构建 Prompt
        prompt = self._build_detection_prompt(sample, fields_context)

        # 第三步：调用 LLM
        try:
            response = requests.post(
                self.config.api_url,
                headers={
                    "Authorization": f"Bearer {self.config.api_key}",
                    "Content-Type": "application/json"
                },
                json={
                    "model": self.config.model,
                    "messages": [{"role": "user", "content": prompt}],
                    "temperature": self.config.temperature,
                    "response_format": {"type": "json_object"}  # 强制 JSON 输出
                },
                timeout=30
            )
            response.raise_for_status()
            raw_text = response.json()["choices"][0]["message"]["content"]
        except Exception as e:
            return RetryResult(
                success=False,
                attempts=1,
                errors=[f"LLM API 调用失败: {str(e)}"]
            )

        # 第四步：解析结果（三层 fallback）
        return parse_llm_json_safely(
            raw_text, LLM检测结果,
            max_retries=self.config.max_retries
        )
要点：response_format: {"type": "json_object"} 是智谱 API 的 JSON Mode，大幅提高结构化输出的成功率。如果 API 不支持，就用三层 fallback 手动解析。
🔎 LLM 异常归因分析（从"有问题"到"为什么"） ~12 分钟

规则引擎告诉你什么数据有问题，LLM 归因分析告诉你为什么有问题以及怎么修。这就是"数据分析师的直觉"被 AI 化。

from dataclasses import dataclass, field
from typing import Optional

@dataclass
class RootCause:
    """根因分析结果"""
    cause_category: str     # 根因分类：数据源问题/ETL逻辑错误/业务变更/数据漂移/未知
    cause_description: str  # 根因详细描述
    affected_scope: str     # 影响范围
    fix_recommendation: str # 修复建议
    priority: str           # 处理优先级：immediate/high/medium/low

@dataclass
class AttributionResult:
    """归因分析结果"""
    root_causes: list[RootCause]
    overall_assessment: str
    action_plan: str        # 行动计划

class AnomalyAttributor:
    """
    异常归因分析器

    数仓思维：就像数据开发工程师排查 ETL 报错，
    先看报错信息，再看上游数据，再分析 ETL 逻辑，
    最后给出修复方案。LLM 帮你自动化这个过程。
    """

    def __init__(self, config: LLMDetectionConfig):
        self.config = config

    def _build_attribution_prompt(
        self,
        rule_results: list[dict],      # 规则引擎的检测结果
        llm_results: list[dict],       # LLM 的检测结果
        table_info: dict                # 表的元信息（表名/字段数/总行数等）
    ) -> str:
        """构建归因分析 Prompt"""

        return f"""你是一位资深的数据开发工程师，专门负责排查数仓数据质量问题。

## 表信息
- 表名：{table_info.get('name', 'unknown')}
- 总行数：{table_info.get('total_rows', 'N/A')}
- 字段数：{table_info.get('total_columns', 'N/A')}
- 数据日期：{table_info.get('date', 'N/A')}

## 规则引擎检测结果（{len(rule_results)} 条异常）
{json.dumps(rule_results[:10], ensure_ascii=False, indent=2)}
{'...（更多省略）' if len(rule_results) > 10 else ''}

## LLM 语义检测结果（{len(llm_results)} 条异常）
{json.dumps(llm_results[:10], ensure_ascii=False, indent=2)}
{'...（更多省略）' if len(llm_results) > 10 else ''}

## 请分析
1. **根因分类**：这些异常最可能的根因是什么？（数据源问题 / ETL 逻辑错误 / 业务规则变更 / 数据漂移 / 其他）
2. **影响范围**：影响多少行/哪些业务场景？
3. **修复建议**：给出具体的修复方案（SQL / 配置变更 / 流程调整）
4. **行动优先级**：哪些问题需要立即处理？

请以 JSON 格式返回：
```json
{{
  "root_causes": [
    {{
      "cause_category": "根因分类",
      "cause_description": "详细描述",
      "affected_scope": "影响范围",
      "fix_recommendation": "修复建议",
      "priority": "immediate/high/medium/low"
    }}
  ],
  "overall_assessment": "整体评估",
  "action_plan": "行动计划（按优先级排序的步骤）"
}}
```"""

    def analyze(
        self,
        rule_results: list[dict],
        llm_results: list[dict],
        table_info: dict
    ) -> RetryResult:
        """执行归因分析"""
        prompt = self._build_attribution_prompt(
            rule_results, llm_results, table_info
        )

        try:
            response = requests.post(
                self.config.api_url,
                headers={
                    "Authorization": f"Bearer {self.config.api_key}",
                    "Content-Type": "application/json"
                },
                json={
                    "model": self.config.model,
                    "messages": [{"role": "user", "content": prompt}],
                    "temperature": 0.2,
                    "response_format": {"type": "json_object"}
                },
                timeout=45
            )
            response.raise_for_status()
            raw_text = response.json()["choices"][0]["message"]["content"]
        except Exception as e:
            return RetryResult(
                success=False, attempts=1,
                errors=[f"归因分析 API 调用失败: {str(e)}"]
            )

        # 解析归因结果（使用 dict 模式，更灵活）
        result = parse_llm_json_safely(
            raw_text, lambda **kw: kw,  # 传入一个 lambda 当"模型"
            max_retries=self.config.max_retries
        )
        return result
设计哲学：归因分析的 Prompt 需要包含三部分信息 — ① 表的元信息（上下文）② 规则检测结果（硬约束异常）③ LLM 检测结果（语义异常）。信息越全，归因越准。
⚙️ 双引擎协同质检（规则 + LLM 完整串联） ~10 分钟

现在把昨天的规则引擎和今天的 LLM 质检器串起来，形成完整的数据质检管线。

from dataclasses import dataclass, field
from typing import Optional
import json
from datetime import datetime

@dataclass
class QualityCheckReport:
    """质检报告（合并规则 + LLM 结果）"""
    table_name: str
    check_time: str = ""
    total_rows: int = 0
    sampled_rows: int = 0
    rule_anomalies: list = field(default_factory=list)
    llm_anomalies: list = field(default_factory=list)
    root_causes: list = field(default_factory=list)
    overall_score: float = 0.0    # 0-100 综合评分
    is_healthy: bool = True
    action_plan: str = ""

    def to_display(self) -> str:
        """生成人类可读的报告"""
        lines = [
            f"{'='*60}",
            f"📊 数据质量检查报告 — {self.table_name}",
            f"{'='*60}",
            f"⏰ 检查时间：{self.check_time}",
            f"📈 数据总量：{self.total_rows} 行，采样：{self.sampled_rows} 行",
            f"",
            f"🔴 规则引擎发现 {len(self.rule_anomalies)} 条异常",
            f"🤖 LLM 发现 {len(self.llm_anomalies)} 条异常",
            f"🔍 根因分析 {len(self.root_causes)} 条",
            f"",
            f"🏆 综合评分：{self.overall_score:.1f}/100",
            f"{'✅ 数据健康' if self.is_healthy else '⚠️ 需要关注'}",
            f"{'='*60}"
        ]
        if self.action_plan:
            lines.append(f"\n📋 行动计划：\n{self.action_plan}")
        return "\n".join(lines)


class HybridQualityChecker:
    """
    双引擎协同质检器

    管线流程：
    1. 规则引擎快速扫描全量数据
    2. 智能采样（异常行优先）
    3. LLM 语义检测（发现规则遗漏的问题）
    4. 异常归因分析（找出根本原因）
    5. 生成综合报告
    """

    def __init__(self, rule_engine, llm_config: LLMDetectionConfig):
        self.rule_engine = rule_engine      # Day59 的规则引擎
        self.llm_detector = LLMDetector(llm_config)
        self.attributor = AnomalyAttributor(llm_config)

    def check(
        self,
        data: list[dict],
        table_name: str,
        fields_context: list[FieldContext]
    ) -> QualityCheckReport:
        """执行完整质检流程"""

        # ====== 阶段1：规则引擎快速扫描 ======
        rule_report = self.rule_engine.run_all(data)
        rule_anomalies = rule_report.anomalies
        suspicious_indices = [a.row_index for a in rule_anomalies]

        # ====== 阶段2：智能采样 ======
        sample = smart_sample(
            data, suspicious_indices,
            sample_size=self.llm_detector.config.sample_size
        )

        # ====== 阶段3：LLM 语义检测 ======
        llm_result = self.llm_detector.detect(
            data=data,
            fields_context=fields_context,
            suspicious_indices=suspicious_indices
        )
        llm_anomalies = []
        if llm_result.success and llm_result.data:
            llm_anomalies = llm_result.data.anomalies

        # ====== 阶段4：归因分析（仅在有异常时触发） ======
        root_causes = []
        action_plan = ""
        if rule_anomalies or llm_anomalies:
            # 准备归因分析的输入
            rule_data = [a.__dict__ for a in rule_anomalies[:15]]
            llm_data = [a.__dict__ for a in llm_anomalies[:15]]
            table_info = {
                "name": table_name,
                "total_rows": len(data),
                "total_columns": len(data[0]) if data else 0,
                "date": datetime.now().strftime("%Y-%m-%d")
            }

            attr_result = self.attributor.analyze(
                rule_data, llm_data, table_info
            )
            if attr_result.success and attr_result.data:
                parsed = attr_result.data
                if isinstance(parsed, dict):
                    root_causes = parsed.get("root_causes", [])
                    action_plan = parsed.get("action_plan", "")

        # ====== 阶段5：综合评分 ======
        total_issues = len(rule_anomalies) + len(llm_anomalies)
        # 评分规则：扣分制，基础100分
        score = max(0, 100 - len(rule_anomalies) * 3 - len(llm_anomalies) * 5)

        return QualityCheckReport(
            table_name=table_name,
            check_time=datetime.now().strftime("%Y-%m-%d %H:%M:%S"),
            total_rows=len(data),
            sampled_rows=len(sample),
            rule_anomalies=rule_anomalies,
            llm_anomalies=llm_anomalies,
            root_causes=root_causes,
            overall_score=score,
            is_healthy=score >= 80,
            action_plan=action_plan
        )
架构要点：双引擎协同的核心是"先规则后 LLM" — 规则引擎毫秒级扫描全量数据，LLM 只处理采样数据。这样既保证了覆盖面（规则），又保证了深度（LLM），同时控制了成本和延迟。

⚠️ 常见陷阱 & 最佳实践 ~3 分钟
陷阱后果对策
给 LLM 全量数据Token 爆炸 + 超时 + 成本失控 智能采样，sample_size ≤ 20
不传字段上下文LLM 无法判断语义是否合理 必须传 FieldContext（含义+范围+规则）
temperature 太高同一数据两次检测结果不一致 质检用 temperature=0.1~0.2
只依赖 LLM 结果LLM 可能漏检明确规则违反 规则优先 + LLM 补充，双引擎协同
归因分析不传规则结果LLM 不知道哪些问题已被发现 规则+LLM 结果都传入归因 Prompt
解析失败不降级整个质检流程因解析异常中断 三层 fallback + 降级返回规则结果

✅最佳实践速查

  • 采样策略：60% 可疑行 + 40% 正常行，保证 LLM 有对比参考
  • Prompt 设计：字段上下文 + 业务规则 + 输出格式要求，三者缺一不可
  • 温度控制：质检用低温度（0.1），归因用稍高温度（0.2）允许更灵活的分析
  • 成本控制：用轻量模型（glm-4-flash）做质检，只在归因分析时用强模型
  • 容错设计：LLM 调用失败时降级为纯规则报告，不阻断业务流程
✏️ 课后练习 ~15 分钟

练习1：增强 LLM 检测 Prompt（中等难度）

在 LLMDetector._build_detection_prompt 中增加"历史异常模式"参数，让 LLM 参考过去发现的异常类型来检测当前数据。提示：在 Prompt 中加入 Few-shot 示例。

练习2：归因结果缓存（中等难度）

为 AnomalyAttributor 添加基于数据指纹（MD5 哈希）的缓存。如果相同数据的归因结果已存在且未过期（1小时内），直接返回缓存结果。提示：用 hashlib.md5(json.dumps(data).encode()).hexdigest() 生成指纹。

练习3：LeetCode #347 — 前 K 个高频元素

给定整数数组 nums 和整数 k，返回出现频率前 k 高的元素。可以按任意顺序返回答案。提示：collections.Counter + most_common(k)，这和统计异常类型频率的思路完全一致。
