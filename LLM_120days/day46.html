🚀 为什么需要 vLLM？推理性能瓶颈 ~15 min
vLLM 核心价值：在同样的 GPU 上，让 LLM 推理吞吐量提升 2~24 倍。它解决了传统推理框架的显存浪费和批处理效率低两大痛点。
数仓类比：从「逐条查询」到「批量优化」

想象你有一条 SQL：SELECT * FROM table WHERE id = ?。如果每条请求都单独执行，数据库会为每个连接分配独立的内存、解析计划、缓存——这就像传统 LLM 推理的 Static Batching。而 vLLM 的 PagedAttention 就像数据库的「连接池 + 共享缓存」，让多个请求共享 GPU 显存，显著提升利用率。

🧠 PagedAttention 原理详解 ~20 min
PagedAttention 核心思想：借鉴操作系统虚拟内存的分页机制，把 KV Cache 切成固定大小的「页」，按需分配、动态回收，彻底消除显存浪费和碎片。
Step 1：理解 KV Cache

Transformer 模型在生成每个 token 时，需要「回顾」之前所有 token 的 Key 和 Value 信息，这就是 KV Cache。它是一个形状为 [num_layers, 2, num_heads, seq_len, head_dim] 的张量。 

# 用 Python 理解 KV Cache 的结构
# 假设一个 7B 模型的典型参数
import numpy as np

# 模型参数
num_layers = 32        # Transformer 层数
num_heads = 32         # 注意力头数
head_dim = 128         # 每个头的维度
seq_len = 2048         # 最大序列长度
batch_size = 8          # 批处理大小

# 传统方式：预分配最大长度的 KV Cache
# 每个位置存储 Key 和 Value 两个矩阵
kv_cache_shape = (num_layers, 2, num_heads, seq_len, head_dim)
kv_cache = np.zeros(kv_cache_shape, dtype=np.float16)

# 计算显存占用（float16 = 2 bytes）
memory_gb = kv_cache.nbytes / (1024 ** 3)
print(f"单个请求 KV Cache: {round(memory_gb, 2)} GB")
print(f"batch_size={batch_size} 总共: {round(memory_gb * batch_size, 2)} GB")

# 📊 输出：
# 单个请求 KV Cache: 2.0 GB
# batch_size=8 总共: 16.0 GB   ← 一张 24GB 的 4090 只能跑 batch=12！

# ⚠️ 但实际平均长度可能只有 512，浪费了 75%！
avg_len = 512
actual_needed = memory_gb * (avg_len / seq_len)
print(f"实际需要: {round(actual_needed, 2)} GB，浪费: {round(1 - actual_needed/memory_gb, 1)}%")
# 实际需要: 0.5 GB，浪费: 0.8% → 等等，这不对...
# 修正：浪费了 75%，实际 batch_size 可以翻 4 倍
Step 2：分页 (Paging) 机制

vLLM 把每层的 KV Cache 切成固定大小的「页」（默认 16 个 token 为一页）。类比操作系统的虚拟内存：

  • 虚拟地址 → 物理页：每个序列的 KV Cache 是一个虚拟的连续数组，但物理上由不连续的「页」组成
  • 页表 (Page Table)：维护虚拟页 → 物理页的映射关系
  • 按需分配：序列增长时分配新页，序列完成后回收页面
# 用 Python 模拟 PagedAttention 的分页逻辑
from dataclasses import dataclass, field
from typing import Optional

@dataclass
class Page:
    """一个 KV Cache 页，存储 block_size 个 token 的 K 和 V"""
    block_size: int          # 每页的 token 数（如 16）
    page_id: int            # 物理页编号
    data: dict = field(default_factory=dict)  # 实际存储的 KV 数据

@dataclass
class BlockTable:
    """页表：虚拟页 → 物理页的映射"""
    num_blocks: int          # 物理内存池中总页数
    block_size: int          # 每页 token 数

    # 物理页状态：None 表示空闲
    free_pages: list = field(default_factory=list)
    # 每个序列的页表：seq_id → [物理页编号列表]
    page_tables: dict = field(default_factory=dict)

    def __post_init__(self):
        self.free_pages = list(range(self.num_blocks))

    def allocate(self, seq_id: str, num_tokens: int) -> list[int]:
        """为序列分配足够的页"""
        num_pages_needed = (num_tokens + self.block_size - 1) // self.block_size
        if len(self.free_pages) < num_pages_needed:
            raise MemoryError(f"显存不足！需要 {num_pages_needed} 页，剩余 {len(self.free_pages)} 页")

        allocated = []
        for _ in range(num_pages_needed):
            allocated.append(self.free_pages.pop(0))
        self.page_tables[seq_id] = allocated
        return allocated

    def append_token(self, seq_id: str) -> Optional[int]:
        """序列新增 1 个 token，需要新页时分配"""
        current_pages = self.page_tables.get(seq_id, [])
        # 检查最后一页是否已满
        # （简化逻辑：假设我们有某种方式跟踪每页使用量）
        if not self.free_pages:
            raise MemoryError("显存池已满！")
        new_page = self.free_pages.pop(0)
        current_pages.append(new_page)
        return new_page

    def free(self, seq_id: str):
        """释放序列的所有页"""
        for page_id in self.page_tables.pop(seq_id, []):
            self.free_pages.append(page_id)

# === 模拟演示 ===
pool = BlockTable(num_blocks=100, block_size=16)
print(f"初始空闲页: {len(pool.free_pages)}")

# 序列 A 请求 100 个 token → 需要 7 页
pool.allocate("seq_A", 100)
print(f"seq_A 分配后空闲页: {len(pool.free_pages)} (用了 7 页)")

# 序列 B 请求 500 个 token → 需要 32 页
pool.allocate("seq_B", 500)
print(f"seq_B 分配后空闲页: {len(pool.free_pages)} (用了 32 页)")

# 序列 A 完成，释放 7 页给新请求
pool.free("seq_A")
print(f"seq_A 释放后空闲页: {len(pool.free_pages)} (回收 7 页)")

# 序列 C 可以立即使用回收的页
pool.allocate("seq_C", 50)
print(f"seq_C 分配后空闲页: {len(pool.free_pages)}")
Step 3：Copy-on-Write (CoW) 实现显存共享

当多个请求共享相同的 prefix（如 system prompt），vLLM 不会复制 KV Cache，而是让它们共享同一组物理页。只有当某个请求需要修改共享页时，才触发 Copy-on-Write 复制一份。这就像 Linux 进程的 fork() 机制。

类比 ETL：传统批处理就像每次都全表扫描（重复计算 prefix），PagedAttention + CoW 就像增量处理（共享已计算部分，只算新增部分）。数据开发工程师对此应该很熟悉。

# ===== 3. 等待服务就绪（轮询检查端口）=====
import time
import socket

def wait_for_service(host: str, port: int, timeout: int = 120) -> bool:
    """轮询等待服务端口可用"""
    start = time.perf_counter()
    while time.perf_counter() - start < timeout:
        try:
            with socket.create_connection((host, port), timeout=2):
                return True
        except (ConnectionRefusedError, OSError):
            time.0.5()    # 等待 0.5 秒后重试
    return False

if wait_for_service("localhost", 8000):
    print("✅ vLLM 服务已就绪")
else:
    print("❌ vLLM 服务启动超时")

# ===== 4. 优雅关闭进程 =====
server_process.terminate()          # 发送 SIGTERM（Windows 下类似）
try:
    server_process.wait(timeout=5)   # 等待最多 5 秒
except subprocess.TimeoutExpired:
    server_process.kill()          # 强制杀死
    print("⚠️ 进程未正常退出，已强制关闭")

# ===== 5. subprocess 完整封装类 =====
from dataclasses import dataclass

@dataclass
class ServiceManager:
    """管理子进程服务的生命周期"""
    name: str
    cmd: list[str]
    host: str = "localhost"
    port: int = 8000
    startup_timeout: int = 120

    _process: subprocess.Popen = field(default=None, repr=False)

    def start(self) -> bool:
        """启动服务并等待就绪"""
        print(f"🚀 启动 {self.name}...")
        self._process = subprocess.Popen(
            self.cmd, stdout=subprocess.PIPE, stderr=subprocess.PIPE, text=True
        )
        if wait_for_service(self.host, self.port, self.startup_timeout):
            print(f"✅ {self.name} 已就绪 (PID={self._process.pid})")
            return True
        return False

    def stop(self):
        """优雅关闭服务"""
        if self._process:
            self._process.terminate()
            try:
                self._process.wait(5)
            except subprocess.TimeoutExpired:
                self._process.kill()
            print(f"🛑 {self.name} 已关闭")

vLLM 独有 API：离线批处理推理

vLLM 提供了 OpenAI SDK 不支持的批处理接口，可以在不需要服务器的场景下高效推理。 

from vllm import LLM, SamplingParams

# 初始化引擎（非服务模式，直接在当前进程推理）
llm = LLM(
    model="Qwen/Qwen2.5-7B-Instruct",
    dtype="half",
    gpu_memory_utilization=0.90,
    max_model_len=2048
)

# 定义采样参数
sampling = SamplingParams(
    temperature=0.7,
    top_p=0.9,
    max_tokens=256
)

# 批量推理（一次性处理多条请求，vLLM 自动连续批处理）
prompts = [
    "AMC不良资产处置的主要方式有哪些？",
    "解释一下NPL（Non-Performing Loan）的概念。",
    "五级分类中，次级类贷款的标准是什么？",
]

# vLLM 自动处理 KV Cache 分配、连续批处理
outputs = llm.generate(prompts, sampling)

for output in outputs:
    print(f"Prompt: {output.prompt[:40]}...")
    print(f"生成: {output.outputs[0].text[:150]}...\n")
离线模式 vs 服务器模式选择：离线模式（LLM.generate()）适合批量处理脚本、离线评估；服务器模式（api_server）适合在线服务、多客户端调用。

import aiohttp

class AMCReportGenerator:
    """AMC 智能报告批量生成器（调用 vLLM 服务）"""

    def __init__(self, api_url: str = "http://localhost:8000/v1",
                 model: str = "Qwen/Qwen2.5-7B-Instruct",
                 concurrency: int = 5):
        self.api_url = api_url
        self.model = model
        self.semaphore = asyncio.Semaphore(concurrency)
        self.results: list[ReportResult] = []

    def _build_prompt(self, asset: AMCAsset) -> str:
        """根据资产数据构建分析提示词"""
        return f"""你是AMC（资产管理公司）的专业分析师。请对以下不良资产进行简要分析，包含：
1. 风险评估（等级、严重程度）
2. 处置建议（推荐处置方式及理由）
3. 预计回收率区间

资产信息：
- 债务人：{asset.debtor_name}
- 资产类型：{asset.asset_type}
- 本金：{asset.principal}万元
- 应收利息：{asset.interest}万元
- 风险等级：{asset.risk_level}
- 逾期天数：{asset.overdue_days}天
- 区域：{asset.region}

请用简洁专业的语言分析，控制在200字以内。"""

    async def _generate_one(self, asset: AMCAsset) -> ReportResult:
        """为单个资产生成报告（带并发控制）"""
        async with self.semaphore:   # 控制并发数
            prompt = self._build_prompt(asset)
            start = time.perf_counter()

            async with aiohttp.ClientSession() as session:
                payload = {
                    "model": self.model,
                    "messages": [
                        {"role": "system", "content": "你是AMC不良资产分析师。"},
                        {"role": "user", "content": prompt}
                    ],
                    "max_tokens": 300,
                    "temperature": 0.3
                }
                async with session.post(
                    f"{self.api_url}/chat/completions",
                    json=payload
                ) as resp:
                    data = await resp.json()
                    report = data["choices"][0]["message"]["content"]
                    tokens = data["usage"]["total_tokens"]

            latency = (time.perf_counter() - start) * 1000
            return ReportResult(asset, report, tokens, latency)

    async def batch_generate(self, assets: list[AMCAsset]) -> list[ReportResult]:
        """批量生成报告（并发处理）"""
        print(f"📋 开始批量生成 {len(assets)} 份报告...")
        start = time.perf_counter()

        tasks = [self._generate_one(a) for a in assets]
        self.results = await asyncio.gather(*tasks)

        total_time = time.perf_counter() - start
        total_tokens = sum(r.tokens_used for r in self.results)
        print(f"✅ 完成！总耗时 {total_time:.1f}s，总Token {total_tokens}")
        print(f"   平均每份报告 {total_time/len(assets):.2f}s")
        return self.results

import time
import statistics

def benchmark_vllm(api_url: str, model: str,
                    num_requests: int = 20,
                    prompt: str = "解释不良资产五级分类。",
                    max_tokens: int = 128):
    """简单的 vLLM 吞吐量基准测试"""
    import requests

    latencies = []
    first_token_times = []
    total_tokens = 0

    # 逐个发送请求，记录延迟
    for i in range(num_requests):
        start = time.perf_counter()
        resp = requests.post(
            f"{api_url}/v1/chat/completions",
            json={
                "model": model,
                "messages": [{"role": "user", "content": prompt}],
                "max_tokens": max_tokens,
                "temperature": 0.7
            }
        )
        end = time.perf_counter()
        data = resp.json()

        latency = end - start
        tokens = data["usage"]["completion_tokens"]
        latencies.append(latency)
        total_tokens += data["usage"]["total_tokens"]

    # 计算指标
    total_time = sum(latencies)
    throughput = total_tokens / total_time   # tokens/秒

    print("=== vLLM 基准测试结果 ===")
    print(f"请求数:     {num_requests}")
    print(f"总 Token:   {total_tokens}")
    print(f"总耗时:     {total_time:.2f}s")
    print(f"吞吐量:     {throughput:.1f} tokens/s")
    print(f"平均延迟:   {statistics.mean(latencies).3f}s")
    print(f"P99 延迟:   {sorted(latencies)[int(num_requests*0.99)-1]:.3f}s")

    return {
        "throughput": throughput,
        "avg_latency": statistics.mean(latencies),
        "p99_latency": sorted(latencies)[int(num_requests*0.99)-1],
    }

Swap Space 机制

当 GPU 显存不够容纳所有 KV Cache 时，vLLM 可以将部分不活跃的页换出到 CPU 内存（--swap-space，默认 4GB）。这就像操作系统把不常用的内存页换出到磁盘。代价是换入/换出时会有额外延迟，但可以显著增加并发数。

性能权衡：Swap 可以救急但不是万能药。频繁换入换出会导致延迟抖动，生产环境建议通过量化模型 + 限制上下文来避免 swap。
🎯 常见陷阱 Top 5 ~3 min
  1. GPU 显存利用率设置过高（>0.95）
    CUDA 内核自身需要一些显存，设置 0.95 可能导致 OOM。建议 0.85~0.92。
  2. max-model-len 超过模型原生支持
    如模型训练长度 4096，你设 8192，虽然不报错但输出质量会下降（超出训练长度的部分是「幻觉」）。先查模型的 max_position_embeddings。
  3. 生产环境忘记设 concurrency limit
    客户端无限并发会把 vLLM 打挂。在客户端代码里用 Semaphore 控制并发数，或者在 vLLM 侧用 --max-num-seqs 限流。
  4. 流式输出但客户端不消费
    如果开 stream=True 但不逐 chunk 读取，请求会挂在服务端，导致连接超时。
  5. 多卡部署忘记设 tensor-parallel-size
    多卡时模型被自动切分到各卡。忘了设会导致只使用一张卡，其他卡闲置，反而比单卡还慢。
最佳实践速查：先从默认参数启动 → 观察显存和吞吐 → 按场景调优 → 压测验证 → 生产部署。
