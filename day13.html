🐍 Python 异常处理：try / except（~1h） 主课
为什么需要异常处理？写代码时，很多事情可能出错：文件不存在、网络断开、API Key 过期、用户输入格式错误……如果不处理，程序直接崩溃。异常处理就是提前预判错误，优雅地兜底，让程序在出错时不会突然死掉，而是给出有意义的提示并继续运行。

1. 什么是异常（Exception）？

异常就是程序运行过程中发生的"意外事件"。Python 内置了很多异常类型，每个类型对应一种错误：

异常类型触发场景举例
FileNotFoundError文件不存在打开一个不存在的文件
KeyError字典中没有这个键dict["不存在的key"]
ValueError值类型对但内容不对int("abc")
TypeError操作类型不匹配"hello" + 123
IndexError列表下标越界[1,2,3][10]
ZeroDivisionError除以零10 / 0
ConnectionError网络连接失败API 调用时网络不通
TimeoutError请求超时API 响应时间过长

2. 基本语法：try / except

核心思路很简单：把"可能出错的代码"放进 try 里，把"出错了怎么办"放进 except 里。 

# 最基本的写法
try:
    result = 10 / 0
except ZeroDivisionError:
    print("不能除以零！")

print("程序继续运行...")  # 不会崩溃，会执行到这里
类比理解：try/except 就像你出门前检查天气。try = "我按原计划出门"，except = "万一下雨了我就带伞"。不管下不下雨，你的行程都不会被完全打乱。

3. 获取具体的错误信息

用 as e 可以拿到异常对象，然后打印出具体的错误描述，方便排查问题： 

# 用 as e 捕获异常对象，打印错误详情
try:
    number = int("不是数字")
except ValueError as e:
    print(f"值错误：{e}")
    # 输出：值错误：invalid literal for int() with base 10: '不是数字'
常见坑：不要写 except:（裸 except），这样会吞掉所有异常（包括 KeyboardInterrupt），你根本不知道发生了什么。至少写 except Exception as e:。

4. 处理多种不同的异常

一段代码可能有多种出错方式，你可以写多个 except 分别处理： 

def read_config(filepath):
    """读取配置文件，处理可能出现的多种异常"""
    try:
        with open(filepath, "r", encoding="utf-8") as f:
            content = f.read()
        config = eval(content)  # ⚠️ 简化示例，实际用 json.load
        return config

    except FileNotFoundError:
        print(f"配置文件 {filepath} 不存在，将使用默认配置")
        return {"default": True}

    except json.JSONDecodeError as e:  # 如果用的是 json.load
        print(f"配置文件格式错误：{e}")
        return None

    except Exception as e:
        print(f"未知错误：{type(e).__name__}: {e}")
        return None


# 测试
config1 = read_config("config.json")     # 文件不存在 → 返回默认配置
config2 = read_config("bad_config.json")  # 格式错误 → 返回 None
重要原则：异常从上到下匹配。Python 会按 except 的顺序依次检查，第一个匹配的就执行。子类异常要放在父类前面，否则永远不会被捕获到。比如 FileNotFoundError 是 OSError 的子类，如果先写 OSError，FileNotFoundError 就永远不会被执行。

5. 完整结构：try / except / else / finally

一共四个块，各有各的职责：

块什么时候执行典型用途
try总是执行放"可能出错的代码"
excepttry 里出错了才执行错误处理/兜底逻辑
elsetry 里没出错才执行放"出错就不该执行的后续逻辑"
finally不管出没出错都执行释放资源/清理工作
# 完整的四块结构
def process_data(filepath):
    result = None
    try:
        # 1. try：可能出错的代码
        data = load_data(filepath)
        result = calculate(data)

    except FileNotFoundError:
        # 2. except：出错了怎么办
        print(f"文件 {filepath} 找不到")
        result = 0

    else:
        # 3. else：没出错时才做的额外操作
        print(f"数据处理成功，结果：{result}")
        save_result(result)

    finally:
        # 4. finally：不管怎样都要做的清理
        print("数据处理流程结束")
        # 比如关闭数据库连接、释放文件锁等

    return result
记忆口诀：try = 试一下，except = 出错了，else = 没出错，finally = 不管怎样。
else 和 finally 都是可选的，不是每次都要写全四个块。

6. 主动抛出异常：raise

有时候你需要主动制造一个错误——当输入不合法时，告诉调用方"你的参数有问题"： 

def calculate_recovery_rate(amount_collected, amount_acquired):
    """
    计算净回收率
    amount_collected: 已回收金额
    amount_acquired: 收购成本
    """
    if amount_acquired <= 0:
        raise ValueError(f"收购成本必须大于0，当前值：{amount_acquired}")

    if amount_collected < 0:
        raise ValueError(f"已回收金额不能为负数，当前值：{amount_collected}")

    rate = (amount_collected - amount_acquired) / amount_acquired * 100
    return round(rate, 2)

# 正常调用
print(calculate_recovery_rate(600, 1000))  # -40.0

# 异常调用
try:
    calculate_recovery_rate(600, 0)  # 会抛出 ValueError
except ValueError as e:
    print(f"参数校验失败：{e}")

7. logging 模块：比 print 更专业的日志

为什么不用 print？print 有几个致命缺点：
1. 无法区分日志级别（哪些是调试信息、哪些是错误）
2. 无法输出到文件
3. 无法记录时间戳和代码位置
4. 正式项目上线后，你需要关掉调试信息但保留错误信息——print 做不到
logging 模块专门解决这些问题。

7.1 五个日志级别

级别数值含义使用场景
DEBUG10调试信息开发时查看变量值、流程走向
INFO20一般信息程序正常运行的关键节点
WARNING30警告不影响运行但有潜在问题
ERROR40错误功能出错了但程序还能继续
CRITICAL50严重错误程序没法继续了
import logging

# ===== 第一步：基本配置（只需执行一次）=====
logging.basicConfig(
    level=logging.DEBUG,           # 最低级别：DEBUG 及以上的都输出
    format="%(asctime)s [%(levelname)s] %(message)s",  # 格式：时间 [级别] 消息
    datefmt="%Y-%m-%d %H:%M:%S"    # 时间格式
)

# ===== 第二步：使用 ======
logging.debug("变量 x 的值是 42")           # 调试信息
logging.info("LLM API 调用开始")            # 正常信息
logging.warning("API 响应时间超过3秒")       # 警告
logging.error(f"API Key 无效：{api_key}")   # 错误
logging.critical("数据库连接失败，程序退出")  # 严重错误

输出效果： 

2026-06-05 09:15:30 [DEBUG] 变量 x 的值是 42
2026-06-05 09:15:30 [INFO] LLM API 调用开始
2026-06-05 09:15:33 [WARNING] API 响应时间超过3秒
2026-06-05 09:15:33 [ERROR] API Key 无效：sk-xxx
2026-06-05 09:15:33 [CRITICAL] 数据库连接失败，程序退出

7.2 日志输出到文件

实际项目中，日志要同时输出到控制台 + 文件： 

import logging

# 创建 logger
logger = logging.getLogger("amc_bot")
logger.setLevel(logging.DEBUG)

# 控制台输出
console = logging.StreamHandler()
console.setLevel(logging.INFO)  # 控制台只显示 INFO 及以上
console.setFormatter(logging.Formatter("[%(levelname)s] %(message)s"))
logger.addHandler(console)

# 文件输出
file_handler = logging.FileHandler("amc_bot.log", encoding="utf-8")
file_handler.setLevel(logging.DEBUG)  # 文件记录所有级别
file_handler.setFormatter(
    logging.Formatter("%(asctime)s [%(levelname)s] %(message)s")
)
logger.addHandler(file_handler)

# 使用
logger.info("程序启动")        # 控制台 + 文件都有
logger.debug("调试信息")       # 只有文件有
logger.error("出错了！")       # 控制台 + 文件都有
生产环境小贴士：正式上线时把控制台级别设为 INFO（不显示 DEBUG），文件级别设为 DEBUG（记录所有信息方便排查）。开发阶段都设为 DEBUG。
🤖 LLM API 调用容错实战（~1-1.5h） 实操
为什么 LLM API 调用需要容错？LLM API 是网络服务，很多事情可能出错：
• 网络不稳定导致请求超时
• API Key 过期或余额不足
• 请求频率过高被限流（Rate Limit）
• 返回的内容格式不是你期望的（比如你想要 JSON，它返回了纯文本）
如果不管这些，你的程序一遇到问题就崩——这在生产环境中是不可接受的。

实战：打造一个健壮的 LLM 调用函数

我们要分4 步，把 Day 7 学的 ask_llm 函数逐步改造成生产级的版本：

1

Step 1：基础异常捕获

给 API 调用加上 try/except，捕获最常见的错误

2

Step 2：超时控制

设置 timeout 参数，防止请求卡死

3

Step 3：重试机制

失败后自动重试（限流/超时类错误重试有意义）

4

Step 4：返回值校验

检查 LLM 返回的内容是否符合预期格式

Step 1：基础异常捕获

import openai
import json
import os
import logging

# 配置日志
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s [%(levelname)s] %(message)s",
    datefmt="%H:%M:%S"
)
logger = logging.getLogger(__name__)

# API Key 从环境变量读取，不要写死在代码里！
client = openai.OpenAI(api_key=os.environ.get("OPENAI_API_KEY", "your-key"))


def ask_llm_v1(system_prompt, user_prompt, model="gpt-3.5-turbo"):
    """
    V1：基础版 + 异常捕获
    捕获 API 调用中最常见的 4 种错误
    """
    try:
        response = client.chat.completions.create(
            model=model,
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": user_prompt}
            ]
        )
        return response.choices[0].message.content

    except openai.AuthenticationError as e:
        logger.error(f"API Key 认证失败：{e}")
        return None

    except openai.RateLimitError as e:
        logger.error(f"请求频率超限：{e}")
        return None

    except openai.APIConnectionError as e:
        logger.error(f"网络连接失败：{e}")
        return None

    except openai.APIStatusError as e:
        logger.error(f"API 返回错误（状态码 {e.status_code}）：{e}")
        return None

    except Exception as e:
        logger.error(f"未知错误：{type(e).__name__}: {e}")
        return None


# 测试
result = ask_llm_v1(
    system_prompt="你是AMC不良资产领域的专家",
    user_prompt="什么是净回收率？"
)
if result:
    print(result)
else:
    print("调用失败，请检查日志")
openai 库的异常体系：openai 把所有错误都封装好了，你不需要处理原始的 HTTP 错误。常用的有：AuthenticationError（认证失败）、RateLimitError（限流）、APIConnectionError（网络问题）、APIStatusError（其他API错误）。

Step 2：超时控制

def ask_llm_v2(system_prompt, user_prompt, model="gpt-3.5-turbo", timeout=30):
    """
    V2：加上超时控制
    timeout=30 表示最多等 30 秒，超时就抛出异常
    """
    try:
        response = client.chat.completions.create(
            model=model,
            messages=[
                {"role": "system", "content": system_prompt},
                {"role": "user", "content": user_prompt}
            ],
            timeout=timeout  # 关键：超时参数，单位是秒
        )
        return response.choices[0].message.content

    except openai.APITimeoutError as e:
        logger.error(f"API 请求超时（{timeout}秒）：{e}")
        return "抱歉，请求超时了，请稍后重试。"

    except openai.RateLimitError as e:
        logger.error(f"请求频率超限：{e}")
        return "请求太频繁，请稍等几秒再试。"

    except Exception as e:
        logger.error(f"调用失败：{type(e).__name__}: {e}")
        return None

Step 3：自动重试机制

import time

def ask_llm_v3(system_prompt, user_prompt, model="gpt-3.5-turbo",
               max_retries=3, retry_delay=2, timeout=30):
    """
    V3：加上自动重试
    - max_retries: 最多重试几次
    - retry_delay: 每次重试间隔几秒（避免连续触发限流）
    - 只有超时和限流类错误才重试（认证错误重试没意义）
    """
    for attempt in range(1, max_retries + 1):
        try:
            logger.info(f"API 调用（第 {attempt} 次尝试）")

            response = client.chat.completions.create(
                model=model,
                messages=[
                    {"role": "system", "content": system_prompt},
                    {"role": "user", "content": user_prompt}
                ],
                timeout=timeout
            )
            logger.info(f"API 调用成功（第 {attempt} 次尝试）")
            return response.choices[0].message.content

        except openai.AuthenticationError as e:
            # 认证错误不需要重试（Key 错了重试 100 次还是错）
            logger.error(f"API Key 认证失败，请检查配置：{e}")
            return None

        except (openai.RateLimitError, openai.APITimeoutError,
                openai.APIConnectionError) as e:
            # 限流、超时、网络错误 → 可以重试
            if attempt < max_retries:
                logger.warning(
                    f"第 {attempt} 次失败（{type(e).__name__}），"
                    f"{retry_delay}秒后重试..."
                )
                time.sleep(retry_delay)
            else:
                logger.error(f"已重试 {max_retries} 次，仍然失败：{e}")
                return None

        except Exception as e:
            logger.error(f"未知错误，不重试：{type(e).__name__}: {e}")
            return None

    return None


# 测试重试机制
result = ask_llm_v3(
    system_prompt="你是AMC不良资产领域的专家",
    user_prompt="解释什么是债转股",
    max_retries=3,
    retry_delay=2
)
重试的设计原则：
1. 不是所有错误都值得重试——认证失败、参数错误重试也没用
2. 要有间隔——连续重试会触发更严格的限流
3. 要有上限——不能无限重试卡住程序
4. 指数退避（进阶）：每次等待时间翻倍（2s → 4s → 8s），更优雅地应对限流

Step 4：返回值校验

def ask_llm_json(system_prompt, user_prompt, model="gpt-3.5-turbo",
                   max_retries=3, timeout=30):
    """
    V4：要求 LLM 返回 JSON 格式，并校验返回内容
    """
    # 在 Prompt 中明确要求 JSON 格式
    full_prompt = f"""{user_prompt}

请严格按照以下 JSON 格式返回结果，不要添加任何其他文字：
{{"answer": "你的回答", "confidence": "高/中/低"}}"""

    content = ask_llm_v3(system_prompt, full_prompt, model, max_retries,
                         retry_delay=2, timeout=timeout)

    if content is None:
        return {"answer": "调用失败", "confidence": "低"}

    # 尝试解析 JSON
    try:
        # 去掉可能的 markdown 代码块包裹
        content = content.strip()
        if content.startswith("```"):
            content = content.split("\n", 1)[1] if "\n" in content else content[3:]
        if content.endswith("```"):
            content = content[:-3]

        result = json.loads(content)

    except json.JSONDecodeError as e:
        logger.error(f"LLM 返回的不是有效 JSON：{e}")
        logger.error(f"原始内容：{content[:200]}")
        return {"answer": content, "confidence": "低"}  # 返回原始文本兜底

    # 校验必要字段
    if "answer" not in result:
        logger.warning("LLM 返回的 JSON 缺少 answer 字段")
        result["answer"] = str(result)  # 把整个结果作为回答

    return result


# 测试
result = ask_llm_json(
    system_prompt="你是AMC不良资产领域的专家",
    user_prompt="什么是债权转让？"
)
print(json.dumps(result, ensure_ascii=False, indent=2))
总结：健壮的 LLM 调用的 4 层防护
第1层异常捕获分类处理不同类型的 API 错误
第2层超时控制防止请求卡死，设置 timeout
第3层自动重试限流/超时自动重试，有间隔有上限
第4层返回值校验检查 JSON 格式和必要字段

3. 写一个测试函数：模拟返回值校验——让 LLM 分别返回正确 JSON 和纯文本，看你的解析函数能不能处理

📖 ToT 思维树（Tree of Thought）（碎片 ~20min） 通勤/午休
前置回顾：Day 12 学了 CoT（Chain of Thought，思维链）——让 LLM 一步步思考。今天学的是 CoT 的"升级版"：ToT（Tree of Thought，思维树）。

从 CoT 到 ToT：为什么要"树"？

CoT 的问题是：它只探索一条思路。就像你解数学题，想到一个方法就直接往下算，算错了就只能重来。

ToT 的思路是：同时探索多条思路，选出最好的那条。就像下棋时你会同时想好几步可能的走法，评估哪步最优。 

CoT（思维链）—— 一条线：
  思考步骤1 → 思考步骤2 → 思考步骤3 → 最终答案
  （如果步骤2想错了，后面全错）

ToT（思维树）—— 多条线 + 评估选择：
  思考步骤1a ──→ 评估 ──→ 思考步骤2a ──→ 评估 ──→ 最优答案
  思考步骤1b ──→ 评估 ✗ （放弃）
  思考步骤1c ──→ 评估 ──→ 思考步骤2c ──→ 评估 ✗ （放弃）

ToT 的三个核心步骤

步骤做什么例子
1. 生成多个思路让 LLM 一次给出多个不同的思考方向"有哪几种方式可以解决这道题？请列出 3 种"
2. 评估每个思路对每个方向打分或判断可行性"方案A的可行性：高/中/低，为什么？"
3. 选择最优路径选最好的方向继续深入选可行性最高的方案，继续下一步思考

CoT vs ToT 对比

维度CoT 思维链ToT 思维树
思考路径一条线，从头到尾多条线，分叉探索
回溯能力❌ 不能回退✅ 发现走错可以换一条路
Token 消耗少多（要生成多条路径）
适用场景简单问题，步骤清晰复杂问题，需要探索比较
实现难度简单，一个 Prompt 搞定复杂，需要多次调用+评估逻辑
面试高频问题："CoT 和 ToT 有什么区别？什么时候用哪个？"
回答要点：CoT 适合步骤明确的线性推理；ToT 适合需要多方案比较的复杂问题（比如创意策划、策略选择）。ToT 本质上是用更多的 Token 换取更高的答案质量。

# Self-consistency vs ToT 的区别（快速理解）
Self-consistency（Day 12 学的）：
  生成5个答案 → 数哪个答案出现最多 → 选最多的那个
  （简单粗暴，但不评估对错）

ToT（今天学的）：
  生成5个思路 → 逐个评估可行性 → 选最优的继续深入
  （更精细，但成本更高）
🧩 LeetCode #1 两数之和（~15min） 刷题

题目：给定一个整数数组 nums 和一个目标值 target，找出数组中和为目标值的两个整数的下标。你可以假设每种输入只会有一个答案。

示例： 

输入：nums = [2, 7, 11, 15], target = 9
输出：[0, 1]
解释：nums[0] + nums[1] = 2 + 7 = 9

思路：哈希表（最优解）

一边遍历数组，一边用字典记录"已经遍历过的数字及其下标"。对于当前数字 x，查找 target - x 是否在字典里——如果在，就找到了答案。 

def two_sum(nums, target):
    """
    哈希表解法：时间 O(n)，空间 O(n)
    核心思路：遍历每个数 x，在字典中查找 complement = target - x
    """
    seen = {}  # {数字: 下标}

    for i, num in enumerate(nums):
        complement = target - num

        if complement in seen:
            # 找到了！返回两个下标
            return [seen[complement], i]

        # 当前数字加入字典，供后续查找
        seen[num] = i

    return []  # 没找到（题目保证有解，这行不会执行）


# 测试
print(two_sum([2, 7, 11, 15], 9))   # [0, 1]
print(two_sum([3, 2, 4], 6))        # [1, 2]
print(two_sum([3, 3], 6))            # [0, 1]
为什么哈希表比暴力法快？
暴力法：两层循环 O(n²)——每个数都和后面所有数相加试一遍
哈希表：一层循环 O(n)——查字典是 O(1)，所以整体 O(n)
技巧：以后遇到"在数组中找两个数满足某种关系"的题，第一时间想哈希表。
